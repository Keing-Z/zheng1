**项目描述**（替换你现在填的版本，更具体）

```
【背景与约束】
学生记账产品的核心矛盾不是功能不足，而是坚持不下去。调研发现多数记账 App 的失败原因是单次记录的操作链路过长，用户平均在 7 天内放弃。因此本项目以"记一笔不超过 3 秒"作为唯一设计约束，所有实现决策都从这条约束推导。

【设计决策与理由】
1. 自绘数字键盘替代系统输入法——系统键盘会遮挡接近半屏并打断操作流，固定键盘可保证金额与分类始终可见；
2. 保存后自动清空输入状态——支持连续记录多笔小额支出（如饭后连续记三笔）；
3. 备注字段设为可选——强制文字输入是用户放弃记录小额支出的首要原因。

【关键技术实现】
· 金额以"分"为单位的整数存储与累加，仅在渲染时格式化，规避 IEEE 754 浮点误差在财务场景下的累积（例如 0.1+0.2 实际结果为 0.30000000000000004）；
· 日期由本地 getter 自行拼接，不使用 toISOString()——后者返回 UTC，在东八区会使凌晨 0–8 点的记账被错误归入前一天；
· 环形占比图以 CSS conic-gradient 实现，不引入 canvas 图表库，减少约 30 KB 运行时依赖与一次重绘；
· 本地优先架构：无后端、无账号、无 CDN 依赖，弱网与断网可完整使用，无服务器成本且用户数据不出设备。

【质量保障】
建立单元、集成、静态三层自动化测试，共 82 项断言，全部通过。集成层在模拟的 wx 运行环境中执行四个页面的完整交互链路（键盘边界、小数去重、退格、保存、分类筛选、跨月切换、删除、预算状态、导出）。

【测试驱动修复的真实缺陷】
1. CSV 导出丢列：表头原以首行字段构造，首行缺失而后续行存在的字段会整列丢失，改为跨全部记录取字段并集；
2. 文本提取顺序反转：原实现先拼接自身文本再拼接子节点，导致 <div><b>X</b> Y</div> 输出为 "Y X"，改为按文档顺序统一维护文本片段与子节点序列；
3. 备份恢复导致数据翻倍：补充基于记录 ID 的去重合并，重复导入时正确跳过重复项。

【完成状态】
功能覆盖收支记录、按日分组账单与分类筛选、环形占比图与 6 个月趋势、月度预算与超支高亮、连续记账天数与成就体系、JSON 备份导出与基于剪贴板的恢复。已提交微信小程序平台审核。
```

**开始时间 / 结束时间**：填你实际做的时间（如果记不清，写 `2026-09` 到 `2026-10`）

**项目描述**

```
【项目内容】
基于 UCI Mushroom 数据集（8124 条样本、22 个分类特征）完成从数据清洗、探索性分析、特征工程到模型评估的完整机器学习流程。使用 Python 与 scikit-learn 实现，代码 706 行，按职责封装为 9 个独立方法。

【技术实现】
· 数据预处理：将 22 个分类特征做中文标签映射，处理以 "?" 编码的缺失值（stalk-root），完成类别编码与标准化；
· 模型对比：在统一预处理流程下训练并评估六种分类器——Logistic Regression、Random Forest、Gradient Boosting、SVM（RBF 核）、KNN、Decision Tree；
· 评估体系：同时计算 Accuracy、Precision、Recall、F1，并使用 5 折交叉验证评估稳定性，绘制 ROC 曲线与 AUC、混淆矩阵；
· 特征重要性：以随机森林不纯度重要性、卡方检验、互信息三种方法独立计算特征贡献度，交叉验证结论一致性；
· 交付物：11 张可视化图表、完整分析报告与基于 Chart.js 的交互式数据看板。

【关键结论（非显而易见的发现）】
六种模型中五种达到 100% 准确率。我没有将这一结果作为成绩汇报，而是先定位其原因：特征重要性分析显示 odor 特征的互信息恰好为 1.0，即该单一特征对标签完全可判别，数据集本身近乎可分，任何树模型都会收敛到同一上限。因此模型对比在此数据集上并不构成模型间优劣的证据。

真正有信息量的结论有三点：
1. 三种方法学上相互独立的重要性度量（基于不纯度的随机森林重要性、基于统计相关的卡方检验、基于信息论的互信息）排序高度一致，均将 odor 列为首位，其后为 spore-print-color、gill-color 与 bruises——多方法一致性比任何单一排序更有说服力；
2. 逻辑回归的 5 折交叉验证得分为 0.9546 ± 0.0066，是唯一未饱和的模型，也是唯一能反映预处理是否有效的模型；
3. 若目标为模型选型而非特征分析，必须更换一个贝叶斯误差非零的数据集，否则比较无意义。

【技术说明】
标准化器仅在训练集上 fit、在测试集上 transform，避免标准化阶段的测试信息泄漏。已记录一处仍存在的局限：类别编码当前在全量数据上 fit，在本数据集上无实际影响（编码仅做类别到整数的映射，与标签无关），但严格做法应仅在训练集上拟合并将未见类别映射至保留值。该点已在项目 README 中明确记录。
```

## 四、项目经历 3：零依赖网页数据采集工具

**项目名称**
```
零依赖网页数据采集工具（Python 标准库实现）
```

**所属机构**
```
个人独立开发
```

**本人角色**
```
独立开发者（架构设计与实现）
```

**开始时间 / 结束时间**：`2026-10` 到 `2026-11`（或按实际）

**项目描述**

```
【背景】
网页数据采集是高频需求（比价、监控、信息聚合），但现有方案普遍依赖 requests、BeautifulSoup、lxml 等第三方库。实际交付场景中，客户环境常受限于内网代理、依赖版本冲突或无法联网安装，导致脚本在客户机器上无法运行。

【方案】
完全基于 Python 标准库（urllib + html.parser）实现整套采集链路，目标是"复制即运行，无需任何安装"。

【技术实现】
1. 自实现轻量 DOM 树：基于 HTMLParser 构建带父子关系的元素树，解析时以单一序列同时记录文本片段与子节点，保证 <div>a<b>x</b>c</div> 按文档顺序输出 "a x c"；
2. 自实现 CSS 选择器子集：支持标签、.class、#id、[attr=value] 四类基本选择器与空格分隔的后代组合；对不支持的运算符（> + ~）明确抛出异常，而非静默返回错误结果；
3. 字段映射 DSL：name=selector 提取文本，name=selector@attr 提取属性，相对链接基于页面 URL 自动补全为绝对地址；
4. 工程健壮性：指数退避的 3 次重试、按页限速、依据响应头识别字符编码、输出带 UTF-8 BOM 的 CSV 以保证 Excel 直接打开不乱码，并支持 --cookie 参数应对需登录页面。

【验证】
26 项离线单元测试全部通过，覆盖 HTML 解析、文本顺序、选择器匹配、字段定义解析与异常输入处理；另以本地 HTML 为数据源完成命令行端到端实跑，正确导出结构化 CSV。

【技术权衡】
以标准库自实现解析器的代价是放弃对完整 CSS 规范与复杂 HTML 容错的支持。这是有意识的取舍：面向"列表页结构化提取"这一主流场景，简化实现已覆盖绝大多数需求，而零依赖带来的交付可靠性收益更高。
```

## 五、项目经历 4：Chrome 扩展

**项目名称**
```
Quick Capture · 网页结构化数据一键采集（Chrome 扩展）
```

**所属机构**
```
个人独立开发
```

**本人角色**
```
独立开发者
```

**项目描述**

```
【功能】
基于 Manifest V3 的浏览器扩展，一键抓取当前页面的结构化数据，按文本 / JSON / CSV 三种格式输出至剪贴板，适用于调研、价格监控与重复性信息录入。

【架构设计】
将纯逻辑与浏览器 API 层解耦：capture.js 不引用任何 Chrome API，仅做 DOM 采集与格式转换，因此可直接在 Node 环境中单元测试，无需启动浏览器；popup.js 负责标签页激活、脚本注入与界面交互。该分层使核心逻辑的 14 项测试可在毫秒级完成，同时降低后续适配其他浏览器的改造成本。

【实现要点】
1. CSV 表头取全部记录字段的并集而非首行字段，避免首行缺字段时整列丢失；
2. 对含逗号、双引号、换行的值按 RFC 4180 规则加引号并转义内部引号，确保 Excel 与 Google Sheets 直接打开不出错；
3. 按最小权限原则仅申请 activeTab、scripting、clipboardWrite、storage 四项权限，不申请任何网络权限，扩展全程不上传数据；
4. 非法选择器、无匹配结果、无活动标签页等情况均有明确错误提示，不出现静默失败。

【验证】
14 项单元测试全部通过，覆盖文本与属性提取、空白规整、空节点跳过、非法选择器异常及三种输出格式的正确性。
```
